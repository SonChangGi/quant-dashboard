# Quant Research Codex Skill Suite

Three manually selected public skills share one adaptive Quant kernel:

- `quant-plan`: read-only audit, quick planning, and decision-complete planning;
- `quant-goal`: one native Goal pursued to verified completion or a genuine
  repeated blocker;
- `quant-developer`: end-to-end implementation and real-surface verification.

There is no fourth team skill. The suite uses host-native subagents and teams
when they are actually useful.

## Invocation

Each `agents/openai.yaml` sets `allow_implicit_invocation: false`. A skill
activates only from the current user's literal `$quant-*` selector or trusted
current-user, same-request metadata generated by that selector. After that
activation, trusted host metadata may continue clarification or steering in
the same unfinished task without another selector. Semantic, plain, quoted,
negated, ordinary prior-turn, unrelated or completed task, Goal, artifact, and
worker context alone do not activate or continue it.

Use `quant-developer` as the ordinary explicit end-to-end implementation entry.
Select `quant-plan` or `quant-goal` alone or alongside Developer when their
read-only planning or native Goal lifecycle is wanted.

Explicitly selected roles compose without widening authority: Plan is
read-only, Developer owns authorized implementation, and Goal owns lifecycle
and overall integration. If plan approval is required before mutation,
implementation waits for a later explicit selection.

## Adaptive default

The public files contain role-specific behavior. Skip the lean kernel at
`shared/references/adaptive-workflow.md` only when inspection shows that no
matching rail could materially change approach, authority, failure handling,
or proof. The kernel:

- grounds work in the actual target and available capabilities;
- asks only for material user-owned decisions;
- negotiates the collaboration surfaces the host actually exposes, using
  subagents for independent lanes, teams only for ongoing coordination, and
  serial fallback when richer surfaces are absent;
- reuses a retained same-role/domain worker only while its context is useful,
  and sends only the changed scope or evidence;
- uses host wait, monitor, or continuation for one-off time/event dependencies,
  and creates automation only when the request authorizes it;
- routes to just the needed analysis, data, UI, automation, publication, or
  public-readback capability rail;
- continues for unmet acceptance or material risk and stops at verified
  acceptance rather than optional polish;
- routes data work to the dedicated free-only policy and proves the actual
  consumer surface.

The default path creates no manifest, ledger, receipt, packet, or workflow
harness. Canonical authority and cost rules live in
`shared/core/authority.md`; routing and opt-in compatibility rules live in
`shared/core/context-routing.md`.

## Legacy compatibility

The source package preserves the established manifests, schemas, templates,
Goal ledger, durable runtime, evidence validators, and team protocol. The
default `base` installation omits that payload. Use it only for an existing
exact project contract, an explicit machine audit, or explicitly requested
contract-specific high-risk recovery. Its identifiers, hashes, versions, and
validators remain authoritative on that path.

When that compatibility path is explicitly needed, install the `compat`
profile at the same established relative paths:

```bash
python3 -B install.py --update --include-legacy
```

Returning to a normal `--update` replaces the shared directory with the lean
base profile and removes compatibility leftovers. Source preservation does not
make legacy machinery a default workflow or justify migrating ordinary work
into it.

## Validate and install

From this directory:

```bash
python3 -B validate_suite.py
python3 -B -m unittest discover -s tests -q
python3 -B install.py --update --dry-run
```

Install the lean `base` profile from committed, reproducible source:

```bash
python3 -B install.py --update --require-clean-source
python3 -B ~/.codex/skills/quant-research-shared/scripts/validate_installed.py
```

The installer validates and stages the three public skills plus the adaptive
kernel, canonical policy, selected capability rails, and installed validator.
It records `install_profile: base|compat`, backs up the previous installation,
replaces each directory with rollback on a caught failure, and verifies
installed hashes. A base install runs the focused public/kernel/installer
contract lane; `--include-legacy` runs the full compatibility regression. The
full unittest command above remains the source-release check. An intentional
development or archive install may omit `--require-clean-source`; its manifest
records dirty or unavailable Git provenance and must not be described as
commit-reproducible.

## Provenance

The suite does not install or depend on LazyCodex or Gajae Code. It adapts
general ideas—explore before deciding, capability-aware delegation, parent-owned
integration, evidence over status, and small persistent surfaces—without
copying their prompts, source, runtime, assets, or fixed orchestration
machinery. Research and licensing notes remain in
`shared/advisory/external-comparisons.md`.
