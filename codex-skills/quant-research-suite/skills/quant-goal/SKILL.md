# Quant Goal

## Activation

Activate only when the current user selects the literal `$quant-goal`, or the
host supplies trusted current-user, same-request metadata generated by that
selector. A semantic match, plain or quoted name, negated example, prior-turn
selection, active Goal, saved artifact, or worker instruction does not activate
the skill.

An explicit selection may initialize, manually resume, or steer one native
Goal. After initialization, the host may automatically continue that active
Goal without reactivating this skill; that is host lifecycle behavior, not
implicit invocation. Do not create Goal state for an ordinary request.

## Bind one native Goal

On every explicit invocation:

1. Call `get_goal` before deciding whether to create, resume, or steer.
2. Express the objective as a concise outcome, material scope and constraints,
   and observable completion conditions. The conditions must be sufficient to
   decide whether required work remains, but have no fixed count or required
   identifier format.
3. If an unfinished Goal exists, reconcile it with the latest user direction
   and fresh evidence. Never create a duplicate.
4. If no unfinished Goal exists, call `create_goal` only because the current
   user explicitly selected `$quant-goal`. Pass `token_budget` only when the
   user explicitly supplied a positive budget.
5. Treat a successful `create_goal` response as binding evidence when it
   unambiguously returns the stored objective. Call `get_goal` again only when
   that response is absent, ambiguous, or insufficient to verify the binding.

Stable condition IDs are optional. Use them only when a condition must be
referenced independently across turns or consumer surfaces, steering can
invalidate only part of its evidence, or a machine-audit contract requires
addressable proof. Otherwise keep the objective readable and concise. When IDs
are active, add a compact live condition-to-evidence map only when multiple
conditions, partial evidence invalidation, or machine-audit proof would
otherwise be ambiguous. Keep it in conversation reporting, not a separate
ledger. Preserve an ID while its meaning is stable, assign a new one only for a
materially changed condition, and refresh affected evidence before completion.
Do not maintain an ID retirement ceremony for ordinary work.

Do not silently replace a materially different active Goal. If the objective,
authority, or cost boundary changes, keep the proposed work pending and ask the
user which Goal to pursue. A compatible refinement may update the working
completion conditions in conversation while preserving the stored objective's
intent.

## Pursue the outcome

For narrow work, use the target's native instructions and tools directly.
Narrow means no capability rail could materially change the chosen approach,
method, or proof. If uncertain, read the kernel's routing table before deciding
to skip it. For non-trivial decomposition, external data, recovery after a
failed route, or proof across several surfaces, read:

- source: `../../shared/references/adaptive-workflow.md`
- installed: `../quant-research-shared/references/adaptive-workflow.md`

The Goal owner retains lifecycle, integration, and final evidence judgment.
Workers receive a bounded outcome, scope, constraints, and expected evidence;
they never call Goal lifecycle tools or declare the overall Goal complete.

If `$quant-plan` is selected in the same request, its read-only phase finishes
first. If `$quant-developer` is selected, it owns the bounded implementation
and returns evidence while this role owns the Goal. Multiple selections never
widen authority.

Continue while a required completion condition is unmet or a material risk
could invalidate the claimed result. Change source, method, tool, or
decomposition after a diagnosed failure. Optional refinements that do not
invalidate acceptance are quality debt, not a reason to prolong the Goal.

## Terminal state

Verify the actual consumption surface promised by the Goal. Local tests do not
prove a remote, deployed, or public result.

Call `update_goal(status="complete")` only when every current completion
condition has fresh material evidence, no material risk invalidates that
evidence, and no required work remains. Do not complete because work is hard,
slow, partly successful, or near a token budget. When a budgeted Goal
completes, report the final token usage returned by the transition.

Call `update_goal(status="blocked")` only when the same blocking condition has
recurred for at least three consecutive Goal turns, no meaningful progress was
made, safe in-scope checks and alternatives are exhausted, and user input or an
external-state change is required. A different blocker or meaningful progress
resets the count. A resumed formerly blocked Goal starts a fresh audit.

`update_goal` is terminal, not steering. Never invent waiting, paused,
cancelled, superseded, or completed host transitions. Token pressure is not a
completion or blocking reason.

## Reporting and compatibility

Report results-first: the achieved or current outcome, important changed or
examined areas, evidence for the completion conditions, and material limits or
the next concrete action. When a live map is active, update it so each current
condition's proof and stale state are clear after steering; otherwise report in
prose.

Native Goal and thread state are the default source of truth. Do not create a
ledger, manifest, receipt, hash-bound team packet, or durable local runtime for
ordinary work. Enter legacy compatibility only for an existing exact contract,
an explicit machine audit, or explicitly requested contract-specific high-risk
recovery, through `../../shared/core/context-routing.md` in source or
`../quant-research-shared/core/context-routing.md` when installed.
