# Quant Goal

## Activation

Activate only when the current user selects the literal `$quant-goal`, or the
host supplies trusted current-user, same-request metadata generated by that
selector. A semantic match, quoted or negated example, ordinary prior-turn
selection, active Goal or artifact, or worker instruction does not activate it.

Explicit selection may initialize, resume, or steer one native Goal.
Continue without another selector only when trusted host metadata proves the
current user's clarification, steering, or native lifecycle work belongs to the
same unfinished, already-active task. This continuation is not implicit
invocation and never creates Goal state for an ordinary, completed, unrelated,
or worker task.

## Bind one native Goal

On every explicit invocation:

1. Call `get_goal` before deciding whether to create, resume, or steer.
2. Record outcome, material scope, constraints, observable completion
   conditions, and a proportional quality bar; use no fixed count or ID format.
3. Reconcile any unfinished Goal with the latest user direction and fresh
   evidence. Never create a duplicate.
4. With no unfinished Goal, call `create_goal` only for the current explicit
   `$quant-goal`; pass `token_budget` only for an explicitly supplied positive
   budget.
5. A `create_goal` response proves binding when it returns the stored objective.
   Call `get_goal` again only when that response is absent or ambiguous.

Stable condition IDs are optional. Use them only when a condition needs to be
referenced independently across turns or consumer surfaces, steering may
invalidate part of its evidence, or a machine audit would otherwise be
ambiguous. When useful, keep a compact
condition-to-evidence map in conversation rather than a separate ledger.
Preserve an ID while its meaning is stable; change it with the condition and
refresh affected evidence.

After steering, report scope, condition, and quality-bar changes, stale proof,
and next action. Within the stored outcome, scope may retire or add conditions
and invalidate affected proof; an outcome-changing expansion is a different
Goal. After a long wait or context compaction, rebuild only the completion view.
Reuse retained evidence only if available and fresh; otherwise mark it stale.
Avoid a fixed snapshot schema in ordinary recovery. A kernel-selected
checkpoint is advisory; native Goal and live evidence remain canonical.

Do not replace an active Goal. If the request is ambiguous, ask which
Goal to pursue. After a clear choice, call `create_goal` only when fresh
`get_goal` shows no unfinished Goal following a host lifecycle action; otherwise
report the limit. Never misuse `complete` or `blocked` to clear the slot.
Compatible refinements may update conditions without replacing stored intent.

## Pursue the outcome

Use target-native instructions for familiar, single-surface work only
after inspection shows no shared capability rail could change its approach,
method, authority, failure handling, or proof. Otherwise read the shared kernel.
If uncertain, read the kernel's routing table before deciding to skip it.

- source: `../../shared/references/adaptive-workflow.md`
- installed: `../quant-research-shared/references/adaptive-workflow.md`

The Goal owner retains Goal lifecycle, integration, and final evidence judgment.
For unfamiliar or multi-lane work, dispatch independent discovery or
verification early while continuing non-overlapping work. Give bounded outcome,
scope, constraints, dependencies, and evidence; workers never call lifecycle
tools or declare overall completion. Use a team for ongoing coordination.

With selected roles, `$quant-plan` finishes read-only work
first, `$quant-developer` owns implementation, and this role owns the Goal.
Composition never widens authority.

Continue while a required completion condition is unmet, a material risk could
invalidate the claimed result, or a material gap against the established
quality bar remains. New evidence may reveal such a gap but does not raise the
bar by itself. Change source, method, tool, or decomposition after a diagnosed
failure. Cosmetic, speculative, or adjacent refinements that do not invalidate
the proportional quality bar are quality debt, not a reason to prolong the
Goal.

## Terminal state

Verify the actual consumption surface promised by the Goal. Local tests do not
prove a remote, deployed, or public result.

Call `update_goal(status="complete")` only when every current completion
condition and the proportional quality bar have fresh material evidence, no
material risk invalidates the result, and no required work remains. Hard, slow,
partial, or near-budget work is not complete. For a budgeted Goal, report the
transition's final token usage.

Call `update_goal(status="blocked")` only when the same blocker recurs for at
least three consecutive Goal turns without meaningful progress, safe in-scope
alternatives are exhausted, and user input or external change is required. A
different blocker or progress resets the count; a resumed blocked Goal starts a
fresh audit.

`update_goal` is terminal, not steering. Never invent waiting, paused,
cancelled, superseded, or completed host transitions. Token pressure is not a
completion or blocking reason.

## Reporting and compatibility

Report outcome, completion evidence, material limits, and next action. With IDs
or a map, update affected proof and stale state; otherwise use prose.

Native Goal and thread state are the default source of truth. For ordinary
work, do not create a ledger, manifest, receipt, team packet, or full durable
runtime. Legacy
compatibility is explicit: use
`../../shared/core/context-routing.md` in source or
`../quant-research-shared/core/context-routing.md` when installed only for an
existing exact contract, explicit machine audit, or explicitly requested
contract-specific high-risk recovery.
