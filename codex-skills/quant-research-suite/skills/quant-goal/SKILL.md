# Quant Goal

## Activation

Activate only when the current user selects the literal `$quant-goal`, or the
host supplies trusted current-user, same-request metadata generated by that
selector. A semantic match, plain or quoted name, negated example, ordinary
prior-turn selection, active Goal, saved artifact, or worker instruction does
not activate the skill.

An explicit selection may initialize, resume, or steer one native Goal. The
host may then continue the already-active role without another selector only
when trusted host metadata proves the current user's clarification, steering,
or native lifecycle work belongs to the same unfinished, already-active task.
This continuation is not implicit invocation and never creates Goal state for
an ordinary, completed, unrelated, or worker task.

## Bind one native Goal

On every explicit invocation:

1. Call `get_goal` before deciding whether to create, resume, or steer.
2. Express the objective as a concise outcome, material scope and constraints,
   and observable completion conditions. The conditions must be sufficient to
   decide whether required work remains, but have no fixed count or required
   identifier format.
3. If an unfinished Goal exists, reconcile it with the latest user direction
   and fresh evidence. Never create a duplicate.
4. If no unfinished Goal exists, call `create_goal` only because the current
   user explicitly selected `$quant-goal`. Pass `token_budget` only when the
   user explicitly supplied a positive budget.
5. A successful `create_goal` response proves binding when it unambiguously
   returns the stored objective. Call `get_goal` again only when the response
   is absent, ambiguous, or insufficient.

Stable condition IDs are optional. Use them only when a condition must be
referenced independently across turns or consumer surfaces, steering may
invalidate only part of its evidence, or a machine-audit contract would
otherwise make proof ambiguous. When useful, keep a compact
condition-to-evidence map in conversation rather than a separate ledger.
Preserve an ID while its meaning is stable, assign a new one only for a
materially changed condition, and refresh only affected evidence. Do not add an
ID retirement ceremony to ordinary work.

After steering or partial invalidation, restate changed conditions, stale
proof, and next action. After a long wait or context compaction, rebuild the
smallest complete view needed to judge completion. Reuse retained
evidence only after confirming it is available and fresh; otherwise mark
it stale. Avoid a fixed snapshot schema.

Do not silently replace a different active Goal. If the request is ambiguous,
ask which Goal to pursue; keep new work pending. After the user
clearly chooses a new Goal, call `create_goal` only when fresh `get_goal` shows
a host lifecycle action left no unfinished Goal; never misuse `complete` or
`blocked` to clear the slot. Otherwise report the limit. A compatible
refinement may update working conditions while preserving stored intent.

## Pursue the outcome

Use the target's native instructions and tools directly only for a familiar,
single-surface task after target inspection shows that no shared capability
rail could materially change its approach, method, authority, failure handling,
or proof. Otherwise read the shared kernel. If uncertain, read the kernel's
routing table before deciding to skip it.

- source: `../../shared/references/adaptive-workflow.md`
- installed: `../quant-research-shared/references/adaptive-workflow.md`

The Goal owner retains lifecycle, integration, and final evidence judgment.
Workers receive a bounded outcome, scope, constraints, and expected evidence;
they never call Goal lifecycle tools or declare the overall Goal complete.

When other public roles are explicitly selected in the same request,
`$quant-plan` finishes its read-only phase first and `$quant-developer` owns
bounded implementation while this role owns the Goal. Composition never widens
authority.

Continue while a required completion condition is unmet or a material risk
could invalidate the claimed result. Change source, method, tool, or
decomposition after a diagnosed failure. Optional refinements that do not
invalidate acceptance are quality debt, not a reason to prolong the Goal.

## Terminal state

Verify the actual consumption surface promised by the Goal. Local tests do not
prove a remote, deployed, or public result.

Call `update_goal(status="complete")` only when every current completion
condition has fresh material evidence, no material risk invalidates that
evidence, and no required work remains. Do not complete because work is hard,
slow, partly successful, or near a token budget. When a budgeted Goal
completes, report the final token usage returned by the transition.

Call `update_goal(status="blocked")` only when the same blocking condition has
recurred for at least three consecutive Goal turns, no meaningful progress was
made, safe in-scope checks and alternatives are exhausted, and user input or an
external-state change is required. A different blocker or meaningful progress
resets the count. A resumed formerly blocked Goal starts a fresh audit.

`update_goal` is terminal, not steering. Never invent waiting, paused,
cancelled, superseded, or completed host transitions. Token pressure is not a
completion or blocking reason.

## Reporting and compatibility

Report results-first: current outcome, relevant areas, completion evidence, and
material limits or the next action. When IDs or a live map are active, update
only affected proof and stale state; otherwise report in prose.

Native Goal and thread state are the default source of truth. For ordinary
work, do not create a ledger, manifest, receipt, team packet, or durable local
runtime. Legacy compatibility is explicit: use
`../../shared/core/context-routing.md` in source or
`../quant-research-shared/core/context-routing.md` when installed only for an
existing exact contract, explicit machine audit, or explicitly requested
contract-specific high-risk recovery.
