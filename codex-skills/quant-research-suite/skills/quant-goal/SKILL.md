# Quant Goal

## Activation

Activate only when the current user selects the literal `$quant-goal`, or the
host supplies trusted current-user, same-request metadata generated by that
selector. Continue without a new selector only when trusted host metadata proves
the current user's clarification or steering belongs to the same unfinished,
already-active task, or a host-native wake or continuation is bound to that same
selector-activated task. Without either, call no lifecycle tool and require a
fresh selector. A semantic match, quoted or negated text, prior-turn selection,
an active Goal or artifact, a completed or unrelated task, or a worker instruction
does not activate or continue it.

## Reconcile native state

On each valid activation or continuation, call `get_goal` before Plan, Developer,
or lifecycle mutation, binding one native Goal first. If one diagnosed safe retry
still fails or is ambiguous, mutate nothing and report native state unconfirmed.

This role owns the Goal lifecycle. Record outcome, material scope, constraints,
observable completion conditions, and a proportional quality bar with no fixed
count or ID format in one compact thread view. Stable condition IDs are optional;
keep a condition-to-evidence map only when useful for several conditions or
machine audit. After steering, report scope and quality-bar changes, stale
evidence, and next action. Within the
stored outcome, scope may add or retire conditions and invalidate affected proof;
an outcome-changing expansion is a different Goal.

If same-versus-different outcome remains ambiguous after safe inspection, mutate
no lifecycle state and obtain the user's classification; never silently choose.

Emit this view after creation, steering, and each blocker turn; include blocker
identity and consecutive-turn count, and never infer missing state.

An active or blocked Goal occupies the slot. Never create a duplicate Goal,
recreate it, or replace it through a terminal state. Resume the same blocked Goal
only on valid activation or trusted continuation, start a fresh blocked audit,
and invent no host transition unless exposed. From fresh `get_goal` state:

- **No unfinished Goal plus explicit selector:** when the request supplies a
  concrete outcome, call `create_goal` once with a self-contained objective
  covering outcome, material scope, completion conditions, and quality bar;
  pass `token_budget` only for an explicit positive budget. Otherwise create
  nothing and ask for the missing outcome and acceptance.
- **Same active or resumed blocked Goal:** reconcile it with current direction,
  compact view, and fresh evidence.
- **Different active or blocked Goal:** create nothing; ask which Goal to pursue
  and report the single-slot limit.
- **No unfinished Goal plus continuation metadata only:** create nothing and
  require `$quant-goal` again.

If the user chooses the occupying Goal, continue it. A different outcome cannot
replace or abandon the slot; start it only after later `get_goal` shows no
unfinished Goal and a fresh selector is present.

Returned intended objective confirms creation. After ambiguity, bind only when
readback matches the full objective with no competing scope; title text alone is
insufficient. Never retry blindly: call `get_goal` again only when reconciling
that mutation. Allow one retry per valid activation or continuation, only after
fresh authoritative readback conclusively confirms non-application for a
diagnosed safe reason. If it is ambiguous, report unconfirmed state and stop.

After a wait or compaction, rebuild only the compact view from native Goal,
retained thread, current target, and live evidence; mark missing or outdated proof
stale. If any condition or quality-bar element stays unrecoverable after safe
inspection, mark the view incomplete and obtain confirmation before terminal
mutation. Do not invent or silently narrow it. A checkpoint is advisory; native
state and fresh evidence are canonical. Before a known wait or compaction that
threatens non-native steering state, route the optional long-running-recovery rail;
if unavailable, obtain confirmation before crossing the boundary. If blocker
identity or count is missing on resume, reset the consecutive count to zero.

## Pursue and compose

Stay in the base workflow only for a familiar single local component and consumer
when inspection settles method, data meaning, authority, failure handling, proof,
and finds no external, shared/public, remote, automation, recovery, or independent
lane. Otherwise read matching shared-kernel routes. If uncertain, read the kernel
routing table before deciding to skip it.

- source: `../../shared/references/adaptive-workflow.md`
- installed: `../quant-research-shared/references/adaptive-workflow.md`

After binding, Quant Plan finishes read-only work; Quant Developer then owns
selected implementation and returns evidence. Without Developer, the Goal owner
may do authorized ordinary work. This role integrates and judges evidence;
workers never call lifecycle tools or declare overall completion. Composition and
delegation never widen authority.

Continue while a required completion condition is unmet, invalidating material
risk remains, or the established quality bar has a material gap. Diagnose before
retrying and change route when needed. Material evidence may refine the bar when
dependable completion requires that change, but never justify optional expansion.
Quality debt does not prolong the Goal.

## Terminal transitions

Verify the promised consumption surface; local proof does not establish a remote,
deployed, or public outcome.

Call `update_goal(status="complete")` only when every condition and the quality
bar have fresh material evidence and no invalidating risk or required work
remains; then report final token usage for a budgeted Goal. Hard, slow, partial,
near-budget, or token-pressured work is not terminal.

Call `update_goal(status="blocked")` only after the same blocker recurs for three
consecutive Goal turns without meaningful progress, safe in-scope alternatives
are exhausted, and user input or external change is required. Progress or a new
blocker resets the count; a resumed blocked Goal starts a fresh audit.

`update_goal` is terminal, not steering. Never misuse `complete` or `blocked` to
clear or free the slot or invent host states. If an update fails, times out, or is
ambiguous, call `get_goal` and claim the requested terminal state only when
readback confirms it. After confirmed non-application, retry only with fresh
acceptance evidence, at most once per valid activation or continuation. If the
retry is ambiguous, report unconfirmed state and stop.

manifest, receipt, team packet, or durable runtime for ordinary work. Use the
legacy router only for an existing exact contract, explicit machine audit, or
